## 二、P0 阻断级缺陷

### 🔴 A19 — `api/store.py` 类体内遮蔽内置 `list`，Web 层无法导入

**位置**　`api/store.py:21` 与 `api/store.py:58`

```python
class DeviceStore:
    def list(self) -> list[dict]:          # 第 21 行: 类体内把 list 绑定为方法
        ...
    def load_from_csv(self, devices: list[dict]):   # 第 58 行: 注解在类体内求值
```

**根因**　Python 在类体执行期间，函数注解是**立即求值**的，名字解析走类命名空间。第 21 行把 `list` 绑成方法后，第 58 行的 `list[dict]` 解析到这个函数对象，`function.__getitem__` 不存在。

**影响**　`api.store` 无法导入 → `api.routes.*` 无法导入 → `api.app` 无法导入。**`./run_web.sh`、`docker compose up`、`uvicorn api.app:app` 全部在启动阶段崩溃**。该缺陷自 v2.2 首个提交 `35cfddd` 起就存在，`api/store.py` 此后从未被修改。

**实测**

```
$ python -m uvicorn api.app:app --port 18080
  File "api/store.py", line 15, in <module>
    class DeviceStore:
  File "api/store.py", line 58, in DeviceStore
    def load_from_csv(self, devices: list[dict]):
TypeError: 'function' object is not subscriptable
```

**修复方向**（三选一，任一即可）：文件头加 `from __future__ import annotations`；把方法改名（`list` → `list_all`，同步改 `routes/devices.py:25`）；注解改字符串字面量 `"list[dict]"`。推荐第一条，改动面最小且同时消除同类隐患。

### 🔴 A20 — `asyncio.as_completed` 与字典键不匹配，任务必然崩溃

**位置**　`api/task_manager.py:126-136`

```python
futures = { loop.run_in_executor(pool, _run_single_device, ...): dev for dev in devices }
for fut in asyncio.as_completed(futures):
    dev = futures[fut]          # 第 135 行
```

**根因**　`asyncio.as_completed()` 产出的不是原始 future，而是内部 `_wait_for_one()` 协程包装器。用它对 `futures` 做键查找恒失败。

**影响**　任务在第一台设备完成时抛 `KeyError`，`_run_task` 协程异常终止（异常还被 asyncio 记为 "Task exception was never retrieved"，不进日志）。后果链：
任务状态永久 `running` → 进度条卡死 → `write_report_files` 从不执行 → `/download/{fmt}` 恒 400 → SSE 无限推送（见 A24）。

**实测**

```
ERROR:asyncio:Task exception was never retrieved
future: <Task finished name='Task-2' coro=<_run_task() ...> exception=KeyError(...)>
  File "api/task_manager.py", line 135, in _run_task
    dev = futures[fut]
KeyError: <coroutine object _AsCompletedIterator._wait_for_one at 0x...>

t+1s status=running completed=0 progress=0.0
t+5s status=running completed=0 progress=0.0
报告文件存在: False
```

> 验证环境为 3.13.14。`as_completed` 自 3.8 起 yield 的就是 `_wait_for_one()` 协程，3.12（Docker/随包运行时）语义相同；建议修复后在 3.12 上补一条端到端用例固化。

**修复方向**　改为 `for fut in asyncio.as_completed(list(futures))` 并用 `futures` 的**原始** future 反查，或直接改用 `asyncio.gather(*futures, return_exceptions=True)` 按索引取 `dev`；更简单的做法是把 `dev` 直接闭包进任务，避免反查。

### 🔴 A21 — `POST /api/devices` 重复关键字，接口恒 500

**位置**　`api/routes/devices.py:47-51`

```python
return DeviceOut(
    **dev.model_dump(),                                  # 已含 password 键
    password="***" if dev.password else "",              # 重复传入
    has_password=bool(dev.password),
)
```

**影响**　`DeviceCreate` 继承自 `DeviceBase` 并声明了 `password` 字段，`model_dump()` 必然带出该键。无论是否填密码，请求都抛 `TypeError`。前端"添加设备"弹窗（`index.html:26`）提交后只会看到 `Internal Server Error`；`app.js:155` 的 `alert("保存失败")` 会显示空消息（`err.detail` 不存在）。

**实测**

```
POST /api/devices {"password": "secret"}  -> 500
POST /api/devices 无 password              -> 500
TypeError: api.schemas.DeviceOut() got multiple values for keyword argument 'password'
```

**修复方向**　`data = dev.model_dump(); data["password"] = "***" if data.get("password") else ""`，再 `DeviceOut(**data, has_password=bool(...))`。注意 `password="***"` 与 `has_password` 语义重复，建议直接返回 `password=""` + `has_password`，避免前端误以为拿到了占位符。

### 🔴 A22 — `/results` 无法序列化，前端结果面板恒 500

**位置**　`api/routes/tasks.py:52-63`，数据来源 `api/task_manager.py:141-147`

**根因**　`task_store.set_result(..., "findings": findings)` 存的是 `[(Rule, [Finding])]` **对象**，`/results` 原样返回。`jsonable_encoder` 对 `Rule` 走 `vars()`（有 `__dict__`），对 `Check` 走 `dict(obj)`（`Check` 用 `__slots__`，无 `__dict__` 且不可迭代）→ 抛 `ValueError`。

**影响**　只要任一设备有 ≥1 条不合规（正常场景），结果接口就 500，前端 `loadTaskResults` 只能显示错误文本。

**实测**

```
GET /api/tasks/t1/results -> 500
ValueError: [TypeError("'Check' object is not iterable"),
             TypeError('vars() argument must have __dict__ attribute')]
```

**修复方向**　入库前转成纯 dict（`rule.to_dict()` + `finding.to_dict()`），或在 `/results` 里显式映射成 `FindingItem`。**注意**：`Rule.to_dict()` 输出的键是 `id`/`sections`/`builtin`，而前端 `app.js:336` 读的是 `rule.rid` / `rule.title`——直接换 `to_dict()` 会让标题变空，需同步对齐字段名。

## 三、P1 高优先级缺陷

### 🟠 A23 — 任务失败没有终态

`_run_task`（`api/task_manager.py:114`）整个函数体没有异常保护。A20、报告写盘失败、快照写盘异常，都会让任务永久停留在 `running`。`TaskStatus.failed` 枚举定义了却从未被赋值。建议：`try/except` 包裹全流程，`except` 分支 `task_store.update(status=failed, message=str(e))`，并把 traceback 写日志。

### 🟠 A24 — SSE 无超时，连接泄漏

`api/app.py:126-135` 的 `while True` 只在 `status in ("done","failed")` 时退出，没有最大时长、没有客户端断开检测（未检查 `request.is_disconnected()`）。配合 A23，**每个启动过的任务都会留下一条永久 SSE 循环**，每秒轮询一次 store。实测 4 秒收到 5 个分片且不终止。建议：加 `MAX_SSE_SECONDS`（如 600s）+ 断开检测 + 终态兜底。

### 🟠 A25 — 存储型 XSS（设备 IP 与配置变量）

三处，全部在 `web/app.js`：

| 位置 | 代码 | 问题 |
|---|---|---|
| 93-94 | `onclick="editDevice('${d.ip}')"` | IP 未转义，单引号即可跳出 JS 字符串 |
| 222 | `value="${esc(String(v))}"` | `esc()` 基于 `textContent→innerHTML`，**不转义双引号**，可注入属性 |
| 211 | `onclick="toggleRule('${r.id}', ...)"` | 规则 ID 来自 `rules.yaml`，可信，风险低 |

**可达路径（实测）**：`POST /api/devices/import` 无字段校验，导入 `ip=x');alert(document.cookie);//` 后 `GET /api/devices` 原样回显，页面刷新即执行。在启用 `VRP_API_TOKEN` 的部署里，令牌存在 `localStorage`，该 XSS 可直接窃取令牌。变量注入路径同理（`PUT /api/profile/variables` 写入含 `"` 的值 → 回写 YAML 合法 → 前端属性被截断）。

**修复方向**　渲染时改用 `textContent` + `addEventListener` 绑定，或对属性上下文做 `escAttr()`（转义 `"` `'` `<` `>` `&`）。不要用内联 `onclick` 拼接用户数据。

### 🟠 A26 — CSV 导入无校验，且"整表替换"具备破坏性

`api/routes/devices.py:100-111`：无表头校验、无字段校验、无大小限制、无编码兜底。

实测三种输入：

| 输入 | 结果 |
|---|---|
| 空文件 | `200 {"count":0}` —— **静默清空全部设备** |
| 非 UTF-8 字节 | `500`（`UnicodeDecodeError` 未捕获） |
| 表头 `a,b,c` | `200 {"count":1}` → 之后 `GET /api/devices` **恒 500** |

第三条的原因：设备字典缺 `platform`，`DeviceOut.platform` 是 `Platform` 枚举，`""` 校验失败：

```
ValidationError: 1 validation error for DeviceOut
platform
  Input should be 's-series' or 'ce-series' [type=enum, input_value='', input_type=str]
```

一旦进入这个状态，**必须重启进程才能恢复**（设备清单在内存里，且每次 `GET` 都 500）。建议：导入前校验表头与 `platform` 枚举、限制文件大小、解码失败返回 400、先构造新列表全部校验通过后再原子替换。

### 🟠 A27 — Docker CLI 用不到用户的 `profile.yaml`

`docker-compose.yml` 的 `cli` 服务挂载了 `devices.csv`、`rules.yaml`、`snapshots`、`output`，**唯独没有 `profile.yaml`**；而 `web` 服务有。README 第四节明确要求 `cp profile.yaml data/`。

后果：用户在 `data/profile.yaml` 里改了 NTP 服务器、SNMP 团体字、规则开关，`docker compose run --rm cli --offline` 读的仍是镜像内 `/app/profile.yaml` 的出厂值 → **判定用的变量与实际环境不一致，报告结论错误且无任何提示**。CI 之所以没暴露，是因为它 `cp profile.yaml data/profile.yaml` 后两边内容相同。

### 🟠 A28 — A07 的修复没有解决 Docker 写配置的问题（待容器验证）

上一轮 A07 把 `profile.yaml` 从 `:ro` 改成读写挂载。但 `_save_profile` 用的是"临时文件 + `os.replace`"（`api/routes/profile.py:177-183`）：

```python
tmp_fd, tmp_path = tempfile.mkstemp(dir=os.path.dirname(_profile_path), ...)
os.replace(tmp_path, _profile_path)     # 目标 /app/profile.yaml 是单文件 bind mount
```

在 Linux 上，对**单文件 bind mount 的挂载点**执行 `rename(2)` 会返回 `EBUSY`（挂载点不能被覆盖）。也就是说容器内 `PUT /api/profile/*` 会抛 `OSError` → 500，与 A07 修复前的现象一致，只是错误从 `EROFS` 变成 `EBUSY`。

**验证状态**：本机无 Docker daemon，未实测。判定依据是 mount namespace 语义，把握较高。建议的稳妥做法：改为"原地写回"（`open(path,"w")` 直接截断写入，配合文件锁）或把整个 `data/` 目录挂载而非单文件。

## 四、P2 中优先级缺陷

### 🟡 A29 — 静默"全部合规"（合规工具的致命失效模式）

`core/engine.py:86-95`：

```python
if platform and platform not in rule.platforms: continue
if device_type and rule.device_type != device_type: continue
```

两个过滤都是"不匹配就跳过"，而调用方对"零规则执行"没有任何检查。实测：

| 输入 | 命中规则数 | 报告结论 |
|---|---|---|
| `device_type="交换机"` | 4 | 正常 |
| `device_type="Switch"`（大小写/拼写错） | **0** | **全部合规** |
| `platform=""`（CSV 该列留空） | 4 | 正常（因为空值不过滤，反而漏了平台约束） |
| `profile.yaml` 缺 `rules` 段 / `rule_ids` 全不匹配 | **0** | **全部合规** |

`devices.csv` 里 `type` 多一个尾随空格（CSV 常见）就会让整台设备"全绿"。对一个合规审计工具，这是最危险的失效方式：**失败不可见**。

建议：`run_all` 返回 `(results, executed_count)`；`executed_count == 0` 时在报告与 API 里显式标注"未执行任何规则（device_type/platform 不匹配）"，并计入错误项而非合规项。

### 🟡 A30 — VLAN1 检查存在漏检

`core/builtin_checks.py:169-209` 只遍历名字匹配 `PHYS` 的接口，且只识别 `port default vlan 1` / `port hybrid pvid vlan 1`。实测配置：

```
interface Eth-Trunk1
 port link-type trunk
 port trunk allow-pass vlan 1 to 4094      ← 放行 VLAN1，未检出
#
interface GigabitEthernet0/0/5
 port link-type hybrid
 port hybrid untagged vlan 1 20            ← 承载 VLAN1，未检出
```

结论 `PASS: 无Vlanif1, 在用端口均未承载VLAN1` —— 两条真实违规都被漏掉。`Eth-Trunk` 被 `PHYS.match(name)` 挡掉，`untagged vlan 1` 不在任何分支的正则里。对一个 high 级规则，这是实质性漏报。建议把 `Eth-Trunk\d+` 纳入视图匹配，并补 `port hybrid (un)?tagged vlan` 的 VLAN1 判定。

### 🟡 A31 — ACL 块切分越界

`_acl_blocks` 用 `re.split(r"(?m)^(?=acl )", cfg)`，切出的片段一直延伸到**下一个 `acl ` 行**，中间的 `interface` / `traffic` 段全被并进来。实测：

```
acl 3000 块内容 = 'acl number 3000\n rule 5 deny udp destination-port eq 67\n#\n
                   interface GigabitEthernet0/0/1\n description 0x86dd test\n#\n'
```

于是 `ipv6_deny_chain` 的 `rule_hit_fn`（找 `0x86dd`）会把接口描述里的字样当成 ACL 命中。建议按 `split_blocks()` 的 `#` 分段结果取块，只认首行以 `acl ` 开头的段。

### 🟡 A32 — 多目标时整改命令非法

`engine.run_rule:35` 把多个目标用 `"; "` 拼成一个 `target`，`render_fix` 再整体塞进 `${if}`。实测输出：

```
interface GigabitEthernet0/0/1; GigabitEthernet0/0/2
 port trunk allow-pass vlan 2 to 4094
```

这条命令贴进设备必然报错。整改文档是给人照抄的，错的命令比没有命令更危险。建议 `Finding` 携带 `targets: list[str]`，渲染时对每个目标展开成独立命令块。

### 🟡 A33 — 未净化的 `ip` 参与路径拼接与网络连接

`core/collector.py:180`、`core/reporter.py:289`：

```python
snap_path = os.path.join(snapshots_dir, f'{dev["ip"]}.cfg')
```

`dev["ip"]` 来自 CSV 或 `PUT /api/devices`，两者都没有格式校验（A35）。实测 `ip="../../evil"` 时：

- `fetch_offline` 成功读到 `snapshots/../../evil.cfg`（越出快照目录）；
- `save_snapshots` 写到 `snapshots/../../evil.cfg`。

受 `.cfg` 后缀约束，能读写的范围是"任意目录下的 `*.cfg`"，危害有限但确实越界。更值得关注的是 `telnetlib.Telnet(dev["ip"], 23)`：无鉴权部署下，攻击者可以把设备 IP 改成任意内网地址，让服务端去连 23 端口（SSRF/端口探测）。建议：`ipaddress.ip_address()` 校验 + `os.path.basename()` 兜底 + 拒绝 `..`。

### 🟡 A34 — `TaskStore` 无淘汰

`api/store.py:79-119` 的 `_tasks` / `_results` 只增不减。每个任务的 `_results` 保存全部 `Rule`/`Finding` 对象图，长跑服务内存单调增长。建议加容量上限（如保留最近 50 个任务）或 TTL 清理。

### 🟡 A35 — 设备 IP 无格式校验

`api/schemas.py:21` 的 `ip: str` 没有任何约束。直接后果：A33 的路径穿越、A25 的 XSS、无效目标进入采集队列。`core/credentials.py:25` 用 `ip.replace(".", "_")` 拼环境变量名，对 IPv6 地址和主机名会生成非法变量名（含 `:` 或 `-`），静默取不到密码。建议 `IPv4Address` 类型或正则校验。

### 🟡 A36 — 非 ASCII 令牌导致 500

`api/app.py:96` 的 `hmac.compare_digest(token, _API_TOKEN)` 对非 ASCII `str` 抛 `TypeError`。实测 `X-API-Token: 中文令牌` → 未捕获异常 → 500。应统一 `encode("utf-8")` 后再比较，或先做 ASCII 校验返回 401。

### 🟡 A37 — SNMP 团体字明文入库与明文回显

`profile.yaml:35-36` 提交了 `snmpRo: Ro@Huawei123` / `snmpRw: Rw@Huawei123`。虽然是模板值，但：
- `.gitignore` 只排除 `devices.csv`，`profile.yaml` 是跟踪文件；
- CI 的卫生检查只匹配 `Huawei@12[0-9]`（设备口令模式），团体字完全不在检查范围；
- `GET /api/profile` 无鉴权时**原样返回**这两个值（`api/routes/profile.py:190`），而默认部署无令牌。

建议：`profile.yaml` 改为 `profile.yaml.example` + 运行时生成；`GET /api/profile` 对 `snmpRo/snmpRw` 做掩码（像设备密码那样返回 `has_value`）；CI 卫生检查扩展到社区字模式。

### 🟢 A38 — `build_report_data` 对设备字典硬取键

`core/reporter.py:47`：`{d["ip"]: ...}`，设备字典缺 `ip` 直接 `KeyError`。当前只能通过 A26 的坏 CSV 触发，但它是"脏数据进内存"的下游放大器。

### 🟢 A39 — 回归测试的有效性不足

1. **HEAD 上直接失败**：`python tests/test_regression.py` → API 段在 `from api.app import app` 处抛 `TypeError`，被 `main()` 捕获后 `return 1`。实测退出码 1。
2. **用例多为源码字符串匹配**：`check("A05", ..., "if idx < 0:" in src and "TelnetTimeoutError" in src)`、`check("A17", ..., 'encoding="utf-8"' in wrapper)`——这类断言只能防止"修复被删掉"，不能发现"代码根本跑不起来"。
3. **A15 用例静默跳过**：`output/baseline_report.xlsx` 不存在时 `skip`，而 CI 的 `cli.py --offline` 生成的是同一路径，实际依赖执行顺序。
4. **无端到端用例**：没有一个用例真正走完 `POST /api/tasks → 轮询 → 下载报告`，A20/A21/A22 三个 P0 因此全部漏网。
5. **会改真实文件**：`run_api_tests` 直接改 `profile.yaml`（虽有备份还原），在 CI 里属于"测试污染工作区"，还原失败会留下脏文件。

### 🟢 A40 — 上一轮审计的"52/52 通过"与事实不符

`docs/AUDIT-2026-10-21.md:242` 记录 `52 / 52 通过`。当前 HEAD 上该套件退出码为 1。两种可能：记录时未包含 API 段，或记录后 `api/` 的导入路径被改动过（`git log -- api/store.py` 显示该文件自 `35cfddd` 未变，故更可能是前者）。无论哪种，**审计报告里的"验证记录"本身需要可复现的证据**，建议把 CI 运行链接或原始输出附在报告里。

## 六、与上一轮审计的关系

上一轮 A01–A18 的修复**在引擎层是有效的**：本轮实测 CLI 离线链路产出与样例声明逐条吻合（`SW-PS-01`、`SW-VLAN1-01` 检出，其余通过），`MULTILINE`、`system` 段合并、DHCP 双向匹配、Excel 列映射均工作正常。

但上一轮存在三个结构性盲区，直接导致本轮 4 个 P0 全部漏检：

1. **只测了"函数"，没测"服务"**。API 用例直接 `import` 路由函数并 `asyncio.run()` 调用，绕过了 `api.app` 的导入链与 ASGI 生命周期——所以 A19（导入失败）、A20（事件循环内行为）、A22（JSON 编码）一个都没碰到。
2. **验证手段偏向源码 grep**。`"if idx < 0:" in src` 这类断言证明的是"补丁还在"，不是"行为正确"。
3. **A07 的修复只改了权限位**，没考虑"原子替换 + 单文件 bind mount"的组合（A28），问题从 `EROFS` 变成 `EBUSY`，现象不变。
