# 代码审计报告 — 华为VRP基线检查工具 v2.2

- **审计日期**: 2026-10-22
- **审计范围**: `core/` `api/` `cli.py` `vrp_baseline.py` `web/` `rules.yaml` `profile.yaml` `tests/` 及部署文件
- **审计方式**: 全量静态阅读 + 在 `/tmp` 临时副本中实证验证（未修改项目源文件）
- **审计性质**: 只读审计，未改动任何代码文件

## 一、结论摘要

**引擎层（`core/`）健康，接口层（`api/`）存在两个必崩缺陷。**

回归测试 27/27 通过说明引擎逻辑正确，但测试覆盖未触及 API 层的真实调用路径——
两个 P0 缺陷都位于"主流程第一次使用就会撞上"的位置：Web 端添加设备、Web 端查看检查结果。

| 级别 | 数量 | 概要 |
|---|---|---|
| 严重 P0 | 2 | `POST /api/devices` 必崩；任务结果接口在有 findings 时必崩 |
| 高 P1 | 5 | 任务永不失败、下载链接鉴权失效、静默 PASS、默认无鉴权、profile 整段替换失败 |
| 中 P2 | 10 | 整改命令渲染错误、并发写竞争、内存无界增长等 |
| 低 P3 | 10 | 废弃 API、死代码、文档与实现不一致等 |

**验证环境说明**: `vendor/pydantic_core/` 中的 `_pydantic_core.cpython-312-aarch64-linux-gnu.so`
为 ARM64 Linux 二进制，Windows 上无法导入 fastapi，因此 API 层回归用例在本机不可执行，
只能依赖 CI（ubuntu-latest）。

## 二、P0 严重缺陷（已实证复现）

### N01 `POST /api/devices` 一定返回 500

- **位置**: `api/routes/devices.py:47`（`create_device`）
- **代码**:
  ```python
  return DeviceOut(
      **dev.model_dump(),
      password="***" if dev.password else "",
      has_password=bool(dev.password),
  )
  ```
- **原因**: `DeviceCreate.model_dump()` 必然包含 `password` 键，与显式传入的 `password=` 冲突。
  CPython 在**调用点**的 `DICT_MERGE` 字节码即抛出
  `TypeError: got multiple values for keyword argument 'password'`，与被调用方实现无关。
- **实证**: `dis` 反汇编确认 `BUILD_MAP` + `DICT_MERGE` 序列；实测任意 `**kw` 可调用对象均抛该错误。
- **影响**: Web 端「添加设备」按钮完全不可用；`POST /api/devices` 恒为 500。
- **建议**:
  ```python
  payload = dev.model_dump()
  payload["password"] = "***" if dev.password else ""
  payload["has_password"] = bool(dev.password)
  return DeviceOut(**payload)
  ```
- **测试缺口**: 回归测试中无任何设备 CRUD 用例。

### N02 任务结果接口恰好在"检查出问题"时崩溃

- **位置**: `api/routes/tasks.py:52`（`get_task_results`）→ `core/models.py:86`
- **原因**: `Finding` 定义了 `__slots__`，没有 `__dict__`。
  `task_store` 中存放的是 `[(Rule, [Finding]), ...]`；该路由无 `response_model`，
  FastAPI 走 `jsonable_encoder`，其兜底路径为 `dict(obj)` → 失败则 `vars(obj)`
  （见 `vendor/fastapi/encoders.py:346-355`）。实测 `Rule` 可 `vars()` 通过，
  `Finding` 两者均失败（`TypeError: vars() argument must have __dict__ attribute`）→ 抛 `ValueError` → 500。
- **影响**: 前端「检查任务」页依赖该接口；设备一旦存在不合规项即为 500，全部合规时反而正常。
  这是最坏的失败模式——只在有问题时失败。
- **建议**（三选一，推荐第一个）:
  1. `Finding` 增加 `to_dict()`，在 `task_manager.set_result` 时就把结果转成可序列化结构（解开与 Web 层的耦合）；
  2. 或给 `Finding` 去掉 `__slots__`；
  3. 或为 `TaskResult.findings` 定义 Pydantic 模型并声明 `response_model`。
- **测试缺口**: 无 API 层序列化用例。

## 三、P1 高危缺陷

### N03 任务永不进入失败态

- **位置**: `api/task_manager.py:114`（`_run_task`）
- **问题**: 整个执行体无 try/except。任何异常（如 `build_report_data` 抛错）都会导致：
  1. `status` 永久停留在 `running`；
  2. `asyncio.create_task` 返回的 future 无人 await，异常无人 retrieve（仅在 GC 时打印）；
  3. `api/app.py:127` 的 SSE `while True` 循环每 1s 推送一次且永不退出 → 连接泄漏；
  4. 前端进度条永久卡住，`status == "done"` 永远不会到达。
- **建议**: 用 try/except 包裹执行体，`except` 分支 `task_store.update(..., status=TaskStatus.failed, message=str(e))`；
  SSE 增加最大时长/心跳上限。

### N04 报告下载链接在启用令牌时失效

- **位置**: `web/app.js:350-351`
  ```html
  <a href="/api/tasks/${taskId}/download/md" class="btn btn-secondary">下载MD报告</a>
  ```
- **问题**: 浏览器导航无法携带 `X-API-Token` 头；服务端开启 `VRP_API_TOKEN` 后该请求被中间件拦为 401。
- **建议**: 下载链接拼接 `?token=...`（与 SSE 一致的做法），或改为 `fetch` + Blob 下载。

### N05 零命中静默 PASS（假阴性）

- **位置**: `core/engine.py:44`（`run_rule` 的 section 遍历）
- **问题**: 当 `select_targets()` 返回空字典时，循环体一次都不执行，规则判定为"通过"。
- **实证**:
  - 配置中无接口块 → `SW-PS-01` 静默通过；
  - 快照不含 `#` 分隔符（整份配置被当成 1 个块）→ 所有接口类规则静默通过。
- **影响**: 合规工具最危险的失败模式。selector 写错、VRP 版本回显格式差异、快照格式异常，
  都会让设备"全绿"，而实际什么都没检查。
- **建议**: `run_all` 对"有 sections 但零目标"的规则产出 `WARN`/`ERROR` 级 finding（如 `未匹配到任何检查目标, 规则未生效`），
  或在报告摘要中单列"未生效规则"计数。

### N06 默认无鉴权 + 绑定 0.0.0.0

- **位置**: `api/app.py:85`、`run_web.sh`、`docker-compose.yml`
- **问题**: `VRP_API_TOKEN` 未设置时 `/api/**` 全开放；服务默认监听 `0.0.0.0:8080`；
  `POST /api/devices` 的 `ip` 字段无格式校验。
- **影响**: 任何能访问该端口的人可添加设备、驱动服务端向内网发起 telnet（受限 SSRF，端口固定 23）、
  下载包含拓扑信息的报告。
- **建议**: 默认监听 `127.0.0.1`；或在无 token 时启动即打印醒目告警；对 `ip` 字段做 `ipaddress` 校验。

### N07 `PUT /api/profile` 整段替换时新键错位并被校验拦截

- **位置**: `api/routes/profile.py:83`（`_update_section`）、`151`（`_save_profile`）
- **问题**: `end` 索引在删除行（`lines[i] = None`）**之前**计算，删除后 `lines` 变短，
  `insert_at = end` 已失效，新键被插入到文件末尾即 `rules` 段内。
- **实证**: 以 `{"ntpServer1": "10.9.9.9", "brandNew": "x"}` + `prune=True` 运行，
  结果 `brandNew` 落入 `rules` 段；随后 `_save_profile` 的回读校验抛 `ValueError` → 整个 PUT 返回 500。
- **评价**: 校验机制拦住了写坏文件（fail-safe 值得肯定），但"新增变量"这一操作实际不可用；
  目前只能通过 `PUT /api/profile/variables`（`prune=False`）新增。
- **建议**: 在 `lines = [l for l in lines if l is not None]` **之后**重新计算插入位置，
  或改为记录"最后一个已知键的行号"作为锚点。

## 六、值得保留的设计（不要改）

1. **分层干净**: `core/` 零 Web 依赖，CLI 与 Web 复用同一引擎，可测试性好。
2. **凭证卫生**: 环境变量 `VRP_PASS_<IP>` + `.gitignore` 排除 `devices.csv` + CI 卫生检查，三重防护。
3. **CORS 默认关闭**: `api/app.py:59-64` 明确注释了 `allow_origins=["*"] + allow_credentials=True` 的危害，取舍正确。
4. **令牌比较用 `hmac.compare_digest`**: 避免时序侧信道。
5. **profile 回写三件套思路正确**: 保留注释 + 临时文件原子替换 + 写前回读校验（虽边界有 bug，但 fail-safe 生效）。
6. **报告按 `task_id` 隔离**: 避免并发任务互相覆盖，下载接口校验任务归属。
7. **采集超时显式失败**: `collector.py:139` 显式判定 `idx < 0`，不用截断配置做合规判定。
8. **回归测试针对历史缺陷编号**（A01~A18），可追溯到审计结论。
